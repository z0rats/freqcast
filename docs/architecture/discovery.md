# Station discovery & stream validation

Everything about `DiscoverStationsScreen`, resolving a pasted URL into a playable stream, and the Radio Browser directory client. This is the single biggest cluster of invariants in the codebase — split out of `AGENTS.md` because it's only relevant when the change touches Discover, Add Station, or `StationUrlResolver`/`WebViewStreamSniffer`. **Check here first for any "can't find/add station from URL" report.**

- `data/RadioBrowserApi.kt`: minimal client for the [Radio Browser API](https://api.radio-browser.info/) (own `OkHttpClient`, `org.json`, not Retrofit/DI). Hits `https://all.api.radio-browser.info/` (round-robins mirrors). `baseUrl`/`client` are constructor params for `MockWebServer` tests.
- `ui/DiscoverStationsViewModel` + `ui/DiscoverStationsScreen.kt` (`DiscoverStationsActivity`, launched from a standalone `AssistChip` atop `MainScreen`'s list): search by name/genre/country/language/nearby, add straight into the library. Chip order `NAME, NEARBY, GENRE, COUNTRY, LANGUAGE`. Debounced 400ms (`SEARCH_DEBOUNCE_MS`). Doesn't `finish()` after each add (multi-add browsing session) — `MainActivity`'s `discoverStationsLauncher` reloads unconditionally on return. Name collisions on add auto-disambiguate (`"Station (2)"`, ...).
- **Default browse (never a blank prompt)**: `DiscoverStationsViewModel.loadDefaultBrowse()` fires once in `init` (gated behind the `autoLoadDefaultBrowse` constructor param, default `true` — off in `DiscoverStationsViewModelTest`'s `createViewModel()` so the many tests asserting an exact `server.requestCount` don't also have to account for this unconditional network call). Shown by `DiscoverResultsContent` whenever `!hasSearched` (before the user's first real search/pick, in *any* mode including GENRE) instead of the old bare `discover_prompt` text: its station list (`defaultBrowseResults`/`defaultBrowseRegionCode`).
  - **GENRE tab's quick-select chips** (`PopularGenresChips`, in `DiscoverStationsScreen`'s persistent per-mode header section alongside `CountryFlagPicker`/the search `TextField` — *not* inside `DiscoverResultsContent`): tappable chips built from `util/GenreCatalog.kt`'s curated, *translated* genre list (`Genre(queryTag, labelRes)`), not a live directory query. radio-browser.info's real `/json/tags` (top tags by station count) was tried first and dropped: it returns whatever free-text station operators worldwide tagged themselves with, mixing languages/scripts unpredictably — reads as "random" clutter rather than a clean single-language row. `GenreCatalog` mirrors `CountryCatalog`'s curated-list shape for the same reason: `queryTag` (an English word, e.g. `"jazz"` — real-world tags overwhelmingly use English regardless of the station's own language) drives the actual `RadioBrowserApi.search(_, SearchBy.TAG)` call, `labelRes` is the localized chip label (en/ru/es/zh-rCN strings). Tapping a chip calls `DiscoverStationsViewModel.searchGenre(tag)`, not `onQueryChange` — the latter would echo the English `queryTag` into the visible GENRE `TextField`, reading as wrong under a chip labeled in the user's own language; `searchGenre` runs the same `runSearch()` search pipeline directly without touching `uiState.query`, same "search without a visible query" shape as `searchNearby()`/the COUNTRY tab's flag picker. `PopularGenresChips` lays the chips out as a single horizontally-scrolling row (no header label), the same compact "genre pill bar" shape as `CountryFlagRow` and as Spotify/Apple Music/YouTube Music's own genre bars — living in the persistent per-mode header rather than one-off empty-state content means it's on screen continuously while the GENRE tab is active, so a multi-row wrap (tried first) ate several rows of vertical space on every single genre search; a slim one-line scrolling strip does not. Being in the persistent header (not the results content) also means the chip row stays visible after a pick, so the user can tap a different genre without having to clear results first — `uiState.selectedGenreTag` (independent of `query`, which `searchGenre` deliberately leaves untouched) tracks which chip to highlight, cleared by `onQueryChange`/`onModeChange` so it doesn't keep pointing at a genre that's no longer what's actually being searched.
  - **Region resolution** (`resolveDefaultBrowseRegionCode()`): an explicit in-app language override (Settings' picker, `AppCompatDelegate.getApplicationLocales()`) wins first — switching the display language to Russian should browse Russian stations even if the device's system region is still `"US"`, otherwise the result reads as "random" stations unrelated to the language just picked. The picker's tags carry language only, no region (`"ru"`, `"es"`), except `"zh-CN"` which already has one; `LANGUAGE_TO_DEFAULT_REGION` fills the gap for the others (`"en"` deliberately absent — ambiguous across US/GB/etc). Only when there's no override ("System default") does it fall through to the device's *raw system* region, `Resources.getSystem().configuration.locales[0].country` — deliberately not `appContext`'s resources, which would already reflect language-only overrides. `CountryCatalog.englishNameForRegion()` (a full ISO 3166-1 alpha-2 lookup, separate from `countries`'s curated 10-flag picker list — doesn't expand that chip row) turns the resolved code into what `RadioBrowserApi.search(_, SearchBy.COUNTRY)` expects; an empty/unresolvable region, or a country search that comes back empty, falls back to `RadioBrowserApi.topStations()` (unfiltered `order=votes`). The header text re-derives a *localized* country name from the stored region code at render time (`Locale.getDisplayCountry(Locale.getDefault())`) rather than reusing the English query string, so a Russian-language UI shows "Россия" not "Russia".
- `util/StreamValidator.kt` probes a URL before `AddStationViewModel.save()` commits (HEAD, falling back to GET for mounts that reject HEAD with 405), closing the response as soon as headers arrive. Runs after the cheap name/URL-taken DB checks; surfaces `error_stream_unreachable` on failure. `Probe.tlsHandshakeFailed` distinguishes an `SSLException` (TLS handshake reset) from a plain unreachable/timeout — observed with at least one RU-hosted station's site resetting the handshake specifically for VPN-routed connections. `AddStationViewModel.resolveStation()` acts on it from two places, gated behind `AddStationViewModel`'s injectable `checkVpnActive: () -> Boolean` constructor param (defaults to `util/NetworkState.kt`'s `isVpnActive(context)`, which checks `NetworkCapabilities.TRANSPORT_VPN` on the active network — injectable so tests don't need a Robolectric `ConnectivityManager` shadow) so `save()` can surface `error_stream_blocked_vpn` instead of the generic `error_stream_unreachable`: (1) the direct probe on the pasted URL itself; (2) stage 5's own TLS signal, which reaches `resolveStation()` through `StationUrlResolver.resolve()`'s `onTlsBlocked` callback — `AddStationViewModel`'s `webViewSniff` wiring lambda wraps `WebViewStreamSniffer.SniffResult.hadTlsFailure` straight into `StationUrlResolver.SniffOutcome`'s own field (see `data/StationUrlResolver.kt` below), no side-channel `AtomicBoolean` involved. Both are checked because the pasted homepage can load fine over TLS while a *different* host its JS talks to (a separate API/backend domain) is the one actually getting blocked — the failure doesn't necessarily show up on the first host contacted. Stages 2-4's own internal `fetchText()` calls don't get this treatment (no equivalent signal threaded out of them).
- **`data/StationUrlResolver.kt` is the entry point for anything a user pastes into `AddStationScreen`'s single URL field** (`stream_url` string res is literally "Stream or website URL") — this is the mechanism to check first for any "can't find/add station from URL" report, before looking anywhere else. `AddStationViewModel.resolveStation()` (`save()`'s helper) tries `streamValidator.probe()` on the typed URL first; only if it's unreachable or not audio content-type does it fall back to `stationUrlResolver.resolve()`, treating the input as a homepage to resolve rather than a direct stream. Resolution order, each stage trying only if the previous found nothing: (1) `fromDirectory` — Radio Browser search keyed off the candidate's `homepage` field, **requires the exact-host match to be unique** among the up-to-50 name-keyword-searched candidates — Radio Browser is community-submitted data and it's common for several distinct stations (regional affiliates of the same network) to all list the same parent-brand homepage, so an ambiguous match (`DirectoryResult.Ambiguous`) stops the pipeline instead of guessing which one the user meant or falling through to a scraped guess that might land on a third, unrelated station: `resolve()`'s `onAmbiguous` callback surfaces the candidate set to `AddStationUiState.candidateStations`, and `ui/components/CandidateStationPickerSheet.kt` (a `ModalBottomSheet`, full-row tap target) lets the user pick one, resolved via `StationUrlResolver.resolveCandidate()` and saved through `AddStationViewModel.selectCandidate()`. A single host-matching candidate whose stream turns out unplayable is a *different* outcome (`DirectoryResult.NoMatch`, not ambiguous) and still falls through to the scraping stages below; (2) `fromHtml` — regex-scans the homepage's raw HTML for `<audio>/<source>` tags, `stream_url`-shaped JSON keys, `.pls`/`.m3u`/`.m3u8` links, bare `.mp3`/`.aac`/`.ogg`/`.opus` URLs, common Icecast ports (8000/8080/8888/9000), or `/stream`/`/listen`/`/live`/`/;stream` paths; (3) `fromLinkedScripts` — same regex scan over same-origin `<script src>` bundles (client-rendered players), plus a probe of any same-domain subdomain found in them for AzuraCast (`/api/nowplaying`) or Icecast (`/status-json.xsl`) status JSON; (4) `fromIframes` — same treatment for third-party `<iframe>` embeds (Zeno.fm/RadioKing/...), skipping an `IFRAME_HOST_BLOCKLIST` of obvious non-player hosts; (5) if `AddStationViewModel` supplied a `webViewSniff` (it does — see `util/WebViewStreamSniffer.kt` below) and stages 1-4 still found nothing, a headless-`WebView` last resort — `fromWebView()`'s ranked candidates first try direct validation, and a captured request that isn't itself playable (e.g. a Supabase/PostgREST JSON endpoint the page's JS called, not the raw stream) falls through to `fromJsonApiResponse()`: replays that exact URL via plain OkHttp with the WebView-captured headers (`apikey`/`Authorization` etc, carried on `SniffedRequest.headers`), then re-runs `extractCandidates()`/`rank()` on the response body — the same `STREAM_KEY_REGEX` that matches `"stream_url":"..."` in HTML/JS text matches unchanged inside a JSON body. That same already-fetched JSON body is also checked for a `logo_url`/`favicon_url`-shaped field (`extractJsonFavicon()`/`JSON_ICON_KEY_REGEX`) and threaded onto the returned `ResolvedStation.favicon` — confirmed real shape (surprise.fm): the same `station_settings` row that names `stream_url` also names `logo_url`, and stage 5's `pageFavicon` backfill (from the *static* HTML's `<link rel="icon">`) never sees this JSON body at all, so an SPA with no such static tag would otherwise resolve a working stream with no icon. Every candidate from any stage is still run through `StreamValidator.isPlayableStream()` before being accepted. A false-positive-shaped string sitting anywhere in a linked script (e.g. a form's placeholder text that happens to look like a stream URL) can pre-empt the AzuraCast/Icecast panel probe in `fromLinkedScripts` (`candidates.isEmpty()` gate) even when that probe would otherwise have been tried.
- **`util/WebViewStreamSniffer.kt`** (stage 5 above, wired in only by `AddStationViewModel` since it needs a `Context`; `StationUrlResolver` itself stays Context-free and takes it as a plain `webViewSniff: (suspend (String) -> SniffOutcome)?` function param, defaulted `null` — `SniffOutcome(candidates, hadTlsFailure)`/`SniffedRequest(url, headers)` live in `StationUrlResolver.kt` so the class doesn't need to import the WebView-holding type; `AddStationViewModel`'s wiring lambda maps `WebViewStreamSniffer.SniffResult` (`CapturedRequest(url, headers)` + `hadTlsFailure`) onto it field-for-field) exists because stages 2-4 are pure regex-over-static-text — a site whose stream URL only ever exists as the result of a runtime JS `fetch()` to an authenticated backend (confirmed case: a Supabase-backed SPA, e.g. `station_settings.stream_url` fetched from Supabase and set on a native `<audio>`, with no literal stream string anywhere in its HTML or JS bundle) is unresolvable by those alone. Loads the homepage in a hidden, hardened `WebView` (`allowFileAccess`/`allowContentAccess`/geolocation off, no popups, `mediaPlaybackRequiresUserGesture = true` so a background resolve can't produce audible sound; explicitly `measure()`/`layout()`'d to a 360×720dp viewport since it's never attached to a window — otherwise it has no size, and `getBoundingClientRect()` below would be meaningless), passively listens via `shouldInterceptRequest` for stream-shaped outgoing requests for `PASSIVE_SETTLE_MS` (1s — deliberately short: `mediaPlaybackRequiresUserGesture` already rules out anything actually gesture-gated starting on its own, so this window only ever catches something that was never gated to begin with) — and since many such players only request the real stream once playback actually starts, `clickPlayControl()` locates anything that looks like a play control (text/aria-label/class matching `play`/`▶`/`слуш`/`listen`/...) via `LOCATE_PLAY_CONTROL_JS` and taps its coordinates with a **real Android-injected `MotionEvent`** (`View.dispatchTouchEvent`), not a JS `element.click()` — Chromium's autoplay policy doesn't count a JS-synthesized click as user activation, confirmed against the Supabase case above (the click heuristic ran, but the gated `play()` never actually fired the stream request). `FALLBACK_CLICK_JS` (the old `element.click()` heuristic) then *always* also runs afterward, not just on a thrown exception — a detached (never-attached-to-a-window) `WebView` has no confirmed-reliable `dispatchTouchEvent` behavior across every OEM/WebView-provider combo, and a silent no-op wouldn't throw, so "no exception" isn't proof the native tap actually reached Chromium. Each captured candidate is kept as a `CapturedRequest(url, headers)` (`request.requestHeaders`, from `shouldInterceptRequest`) rather than a bare URL — `StationUrlResolver.fromJsonApiResponse()` needs those headers to replay a JSON API request outside the WebView, see above. `shouldInterceptRequest` excludes `OPTIONS` requests from capture (`request.method`) — confirmed on a real device (surprise.fm) that a browser-generated CORS preflight hits the *same URL* as the real request that follows it, arriving first, with its `Access-Control-Request-Headers` value merely listing `apikey` as a header name the real request will carry rather than an actual credential; left uncaptured so it can never win `runSniff`'s `distinctBy`-by-url dedup over the real, credentialed request for the same URL (a preflight-headers replay 401s against Supabase/PostgREST). `SniffResult.hadTlsFailure` (set via `WebViewClient.onReceivedSslError`/`onReceivedError`, classified by the pure `isTlsHandshakeError(errorCode)`, always still `handler.cancel()`s — never weakens the check) is `AddStationViewModel`'s second TLS-block signal, see `util/StreamValidator.kt` above. Request capture itself (`shouldInterceptRequest`) is gated by the pure `shouldCaptureRequest(url, method)` (folds in the OPTIONS-preflight exclusion below), and the final candidate list is `finalizeCandidates()` (dedup-by-url + cap) — all three, plus `isCandidateStreamUrl`, are the full set of what's decidable here without a real `WebView` and are unit tested (`WebViewStreamSnifferTest`); the orchestration around them (page load, JS execution, touch dispatch) is not, see `AGENTS.md`'s Testing section. **Diagnostic logging** (`Log.d`/`Log.w`, tag `WebViewStreamSniffer`): every intercepted request (candidate or not), `onPageFinished`, every `onConsoleMessage` (surfaces the page's own JS errors — e.g. an uncaught promise rejection from a gesture-blocked `play()`), `onReceivedSslError`/`onReceivedError`, `locatePlayControl`'s match (or lack of one), the native `dispatchTouchEvent`'s consumed/not-consumed return values, the fallback JS click's return value, and the final `SniffResult` — this is the only way to diagnose a "found nothing" report without guessing; `adb logcat -s WebViewStreamSniffer:D chromium:I` when reproducing one. Cookies/storage are wiped after every call (`CookieManager.removeAllCookies` + `WebStorage.deleteAllData`) so repeated resolves for different stations can't cross-contaminate. **Accepted risk**: this automatically executes arbitrary, unattended third-party JavaScript from whatever URL the user pastes, and the synthetic tap may hit the wrong element on an untrusted page — a materially larger trust surface than stages 1-4's plain-text fetches. Deliberate trade-off, not an oversight; mitigated by the hardening above plus running headless/never attached to a `ViewGroup`. Not guaranteed to work — a best-effort last resort, not a full fix for stages 2-4's static-text ceiling.
- `util/CountryFlagEmoji.from(code)`: pure function, 2-letter ISO code → flag emoji via the Unicode regional-indicator offset, `null` for anything malformed. `DiscoverStationsScreen`'s `stationSubtitle()` shows just the flag (no country name text) when available; `codec` folds into the same subtitle's bitrate segment (`"128 kbps MP3"`).
- `RadioBrowserStation.votes` feeds a star badge (`util/VoteCountFormatter.format()`) shown when `votes > 0`; `search()` sorts by `order=votes` so the visible ranking matches the badge.
- `RadioBrowserStation.homepage` surfaces as an `OpenInNew` icon button (`Intent.ACTION_VIEW`, caught against `ActivityNotFoundException`). Presentation-only, not persisted.
- `RadioBrowserStation.favicon` feeds the icon pipeline for Discover adds: `RadioBrowserApi.downloadFavicon()` (returns `null` on any failure, never throws) + `IconStorage.saveImageBytes()` (shares `saveImage()`'s downscale-to-512px-JPEG internals). Fired fire-and-forget from `addStation()` (child of the insert's `viewModelScope.launch`) — station shows the auto-generated emoji immediately, `customIcon` backfills once the download finishes or never if it fails. `DiscoverStationsViewModel` is the only ViewModel holding a `Context` (`appContext`, always `applicationContext`), needed for `IconStorage`.
- **"Near me" search** (`DiscoverSearchMode.NEARBY`): no text query — `DiscoverStationsScreen` hides the `TextField` and drives a one-shot permission-then-search flow. A `LifecycleEventObserver` retries `requestNearbySearch()` on every `ON_RESUME` while `mode == NEARBY` and the last failure was `discover_location_unavailable` (so returning from Settings with GPS now on "just works"); reads `uiState` via `rememberUpdatedState` since the `DisposableEffect` is keyed only on `lifecycleOwner`. `RadioBrowserApi.searchNearby()` uses `geo_lat`/`geo_long`/`geo_distance`/`order=distance`; `distanceKm` populates only for this call, shown as `"📍 2.3 km"`. Search radius (`NEARBY_RADIUS_METERS`) is hardcoded 50km.
- `util/LocationProvider.kt` wraps plain `android.location.LocationManager` (not `FusedLocationProviderClient` — avoids a new Play Services dependency). Prefers cached `getLastKnownLocation()` over `requestSingleUpdate()`; never requests continuous updates or persists a coordinate. Gates on `ACCESS_COARSE_LOCATION` only (deliberate privacy tradeoff — city-level precision is enough). `DEFAULT_TIMEOUT_MS = 20s` (a cold-start GPS fix can realistically take 15-20s; 10s cut searches off prematurely). **Emulator note**: the simulated GPS provider produces no fix from the in-app location toggle alone — set a location via Extended Controls → Location.
- Permission flow lives in `DiscoverStationsScreen` (ViewModel has no Android permission APIs): `ContextCompat.checkSelfPermission` → rationale `AlertDialog` if ungranted → `RequestPermission()` launcher. On grant, calls `searchNearby()` directly; on denial, `onLocationPermissionDenied()` sets an inline hint under the chip row.
- `LocationProviderTest` needs two non-obvious Robolectric fixes: (1) permission grant/deny via `Shadows.shadowOf(application).grantPermissions()/denyPermissions()` — `ShadowApplicationPackageManager.grantRuntimePermission()` doesn't affect `ContextCompat.checkSelfPermission()` under this Robolectric version; (2) `ShadowLocationManager.simulateLocation()` posts to the `Looper` it was registered against, and Robolectric's main looper is paused by default — needs an explicit `Shadows.shadowOf(Looper.getMainLooper()).idle()` after `simulateLocation()`, or the callback never fires (silently eaten by the internal 5s timeout).
- `RadioBrowserStation.sslError` surfaces as a `Warning` icon (tinted `colorScheme.error`) next to the homepage link — non-blocking, since the directory's HTTPS check failing doesn't guarantee ExoPlayer will also fail. Presentation-only.
- **GENRE tab's real-tag autocomplete** (`TagSuggestionsList`, replacing `PopularGenresChips` in the same header slot whenever the typed text matches cached tags): backed by `RadioTagRepository`/`RadioTagDao`'s local cache (`radio_tags` table, schema v11) of the directory's full `/json/tags` catalog (~11.9k entries) — the language-mixing objection above only rules out using it for the *curated chip row*, not for suggesting real matches once the user is already typing an (often English) query. `RadioBrowserApi.fetchTags()` **must** pass an explicit `limit` (currently 50000): a bare `/json/tags` call silently truncates to the server's default 1000 rows, alphabetically first (mostly punctuation-prefixed junk) — confirmed live, doesn't even include "jazz". `DiscoverStationsViewModel.syncTagsIfNeeded()` populates the cache once per cold start, gated on the cached row count being ≥ `MIN_HEALTHY_TAG_COUNT` (2000) rather than just non-empty, so a stale/truncated cache from a bad prior fetch re-syncs on the next launch instead of being treated as permanently "already synced". `updateTagSuggestions()` re-queries `RadioTagDao.searchByPrefix()` on every keystroke while in GENRE mode (no debounce needed, pure local read); picking a suggestion (`onTagSuggestionSelected`) fills the visible query and calls `searchGenre()` directly, same as a chip tap.
