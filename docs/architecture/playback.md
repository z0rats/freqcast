# Playback architecture

`RadioPlaybackService`, its narrow `PlaybackController` seam, retry/reconnect, Android Auto, and the home screen widget — everything that touches the playback pipeline. Split out of `AGENTS.md` because it's only relevant when the change actually touches playback; see `AGENTS.md`'s own Architecture conventions for what stays cross-cutting.

## Service core

- `RadioPlaybackService` (a `MediaLibraryService`, see Android Auto below) exposes `playbackSnapshot: StateFlow<PlaybackSnapshot>` as the single source of truth for reactive UI — screens collect this instead of polling. Delegates to `playback/TimeshiftController` (buffer/seek for rewind-live) and `playback/PlaybackStateStore` (SharedPreferences; last-started station so `onStartCommand` can resume after the system kills+restarts the service with a null intent — this is what survives process death, not just backgrounding). That resume branch only fires when `player.playbackState == Player.STATE_IDLE` (true right after a fresh `onCreate()`) — a null/extra-less intent arriving while playback is already active is logged and ignored rather than tearing down and re-requesting the already-buffering/playing stream; what actually delivers such an intent mid-playback (observed on-device, all 4 `startForegroundService` call sites always pass `EXTRA_STREAM_URL`) is still unconfirmed.
- **`PlaybackRequest`** (`stationName`, `streamUrl`, `customIcon`, `knownHls`) is the one value `startPlayback()`/`applyPlayback()` take — the service's `currentRequest: PlaybackRequest?` field (set by `applyPlayback` itself) replaced two separately-set `stationName`/`currentCustomIcon` mutable fields every call site had to remember to set, in order, before calling in. Every read site (notification title/text/large-icon, the `PlaybackActivity` `PendingIntent` extras, `updateWidget()`, `getCurrentStationName()`, media-item metadata) reads `currentRequest?.stationName`/`currentRequest?.customIcon`. `stopPlayback()` deliberately leaves `currentRequest` untouched — `getCurrentStationName()` and the widget still need to name the last-played station after an explicit stop. `attemptScheduledRetry()` reuses `currentRequest`'s name/icon via `.copy(streamUrl = ..., knownHls = ...)`, sourcing the (always-identical) stream URL/HLS hint from `ConnectionRetryPolicy`'s own tracked `RetryTarget`.
- **Playback UI never sees the raw `RadioPlaybackService`** — `ui/playback/controller/PlaybackController.kt` is the narrow seam Compose/Activity code binds through instead: `toggle(station)`, `stopPlayback()`, `seekBackward`/`seekToLive`/`seekToOffsetFromLive`, `setSleepTimer`/`cancelSleepTimer`, `currentClipFormat`/`exportClip`, plus `playbackSnapshot`/`getCurrentStationName()` for reads. `ServiceBackedPlaybackController` (main) is the production adapter; `FakePlaybackController` (test source set) is the second adapter that makes the seam real, not hypothetical. `MainScreen`/`PlaybackScreen`/`NowPlayingContent`/`ClipExport` all take `PlaybackController?`, never `RadioPlaybackService?`.
  - `toggle(station: RadioStation): ToggleResult` (STARTED/STOPPED/NETWORK_UNAVAILABLE) replaces three previously-independent toggle implementations (`MainActivity.playStation`, `PlaybackActivity.togglePlayback`, `NowPlayingBottomBar`'s click wiring) with one pure decision, `decideToggleAction()` (`internal`, unit-tested in `PlaybackControllerLogicTest` — same "pure state machine" shape as `ConnectionRetryPolicy`): compares by stream URL against `PlaybackSnapshot.currentMediaId`, checking "is this station already playing" *before* the network check, so stopping never needs a network. `PlaybackActivity.togglePlayback`'s old version compared only "is *anything* playing" rather than by URL — a latent bug (could stop the wrong stream) fixed by consolidating onto one decision.
  - `rememberPlaybackController()` is the one shared bind/unbind Composable (`DisposableEffect` + `LifecycleEventObserver` on ON_START/ON_STOP, mirroring the binding it replaces) — both `MainActivity` and `PlaybackActivity` call it instead of hand-rolling `ServiceConnection`/`bindService`/`unbindService`. It accepts an optional external `MutableState<PlaybackController?>` to write into: `PlaybackActivity` supplies one (`playbackControllerState` field) because its `onResume()`/`onNewIntent()` run outside Compose and need the current controller synchronously (`syncFromService()`); `MainActivity` has no such need and uses the default internally-`remember`ed state. Must be read via Compose state, not a plain `var` — `onServiceConnected` fires after first composition.
  - `ui/components/PlaybackPresentation.kt`'s `ConnectionErrorToastEffect(connectionErrorAt)` is the one shared "connection failed" Toast (deduped by timestamp), replacing a near-identical `LaunchedEffect` block that used to be copy-pasted in both `MainScreen` and `PlaybackScreen`.
- Reconnect-on-network-loss uses capped exponential backoff (`playback/ConnectionRetryPolicy.retryDelayMs`: 2s/4s/8s/16s, capped 30s, `MAX_RETRY_COUNT = 5`) — not infinite retry. `RadioPlaybackService` owns the `ConnectivityManager.NetworkCallback` and `Handler.postDelayed` scheduling; `ConnectionRetryPolicy` is the pure state machine deciding what to do (`RetryDecision`: `RetryNow`/`RetryAfter`/`GiveUp`/`NoAction`), keyed by a monotonic attempt id so a scheduled retry that's since been superseded by a station switch or a fresh play (`onPlaybackStarted`) is a no-op instead of firing against the wrong stream.
- `startForegroundWithNotification()` (called from `applyPlayback` and the `PlayerNotificationManager` listener) returns `Boolean`, not `Unit` - Android 12+ can throw `ForegroundServiceStartNotAllowedException` from `startForeground()` itself when the call isn't backed by a currently-valid background-start exemption, observed in practice from both of this service's background-triggered restart paths: the network-recovery retry above (`Handler`/`NetworkCallback` callback, not user-visible) and `onStartCommand`'s null-intent process-death resume. Caught as a plain `Exception`, not that specific type - referencing an API-31-only exception class in a `catch` can trip ART's eager verifier below minSdk 31 (this app's minSdk is 29). Both call sites treat a `false` return the same as a `RetryDecision.GiveUp`: call `stopPlayback()` (and `return` at the `applyPlayback` call site, before building out the player/media-session pipeline) instead of proceeding as if playback had actually started.
- `PlaybackActivity` opened from the mini player uses a custom slide-up-from-bottom transition (`res/anim/slide_up_in.xml`+`stay.xml`, via `ActivityOptionsCompat.makeCustomAnimation`); `finish()` is overridden to play the reverse (`slide_down_out.xml`, classic `overridePendingTransition` — not API-34's `overrideActivityTransition`, since minSdk is 29), covering every close path (back arrow, system back, programmatic `finish()`). Other entry points (notification, widget, App Shortcuts, Android Auto) skip the slide-up enter (no mini player to expand from) but keep the slide-down close.
- `RadioBrowserStation.hls`/`isHls`: `onStartCommand`/`startPlayback`/`applyPlayback` only ever receive a bare stream URL (every caller passes `EXTRA_STATION_NAME`/`EXTRA_STREAM_URL` strings, never a full `RadioStation`), so `onStartCommand` resolves the HLS hint via `repository.getStationByUrl()` before calling `startPlayback`. Android Auto's `playFromBrowseTree`/`onAddMediaItems` pass `station.isHls` straight from in-memory `cachedStations`, skipping the DB round-trip. A network-loss retry reuses the cached `currentKnownHls` rather than re-resolving (so retry can't flip-flop the decision).
- `RadioBrowserApi.registerClick(uuid)` reports a play to the directory's `clickcount` metric (separate from `votes`, which `search()` sorts by). Fire-and-forget, swallows `IOException`. `radioBrowserUuid` is resolved via the same `getStationByUrl()`/`cachedStations` plumbing as `isHls`. Only fired from direct-play (`onStartCommand`) and `playFromBrowseTree` — **not** from process-restart resume (`playbackStateStore.restore()`), to avoid double-counting on cold start.
- **Notification skip-next/skip-previous** (the media-style notification's compact-view buttons): the player only ever has one `MediaItem` loaded (the live stream, not a real playlist), so `hasNextMediaItem()`/`hasPreviousMediaItem()` are always false and ExoPlayer's own `COMMAND_SEEK_TO_NEXT`/`COMMAND_SEEK_TO_PREVIOUS` report unavailable by default — `TimeshiftSeekPlayer` (the `ForwardingPlayer` wrapper, same one used for the timeshift `seekBack`/`seekForward` reroute above) force-enables both and overrides `seekToNext()`/`seekToPrevious()` to call `RadioPlaybackService.switchToAdjacentStation(StationNavigator::next / ::previous)` instead. `setupNotificationManager()` additionally calls the *instance* methods `setUsePreviousActionInCompactView(true)`/`setUseNextActionInCompactView(true)` (not `Builder` methods - a different part of the media3 API) so the buttons actually render in the collapsed notification-shade view, not just the expanded one (`usePreviousAction`/`useNextAction` already default `true`, so the expanded view shows them automatically once the commands report available).
  - "Next/previous station" means the plain station list in its current order (`sortOrder ASC, id ASC` — no separate "favorites" concept, see List ordering above), navigated via the already-widget-tested `StationNavigator.next`/`.previous`, wrapping at either end. `switchToAdjacentStation` calls `applyPlayback` directly, not `startPlayback` — same reasoning as `playFromBrowseTree`: it fires from inside `PlayerNotificationManager`'s button-click callback, so rebuilding the session mid-dispatch isn't the safe path.
  - **`stationSwitchMutex`-serialized**: `repository.getAllStations()` is a real suspend Room query, so a second rapid tap (e.g. double-tapping "previous" before the first tap's `applyPlayback` has landed) would otherwise read the same not-yet-updated `currentRequest` as the first tap and compute the same target station twice, silently dropping one of the two taps — caught by `RadioPlaybackServiceAutoTest`'s two-back-to-back-`previous`-calls assertion. The mutex makes each call wait for the previous one's `currentRequest` write before reading it, so N rapid taps walk N stations.

## Android Auto

- `RadioPlaybackService extends MediaLibraryService` (not plain `MediaSessionService`) so the station list is browsable from a head unit. Manifest intent-filter action is `androidx.media3.session.MediaLibraryService` (plus `android.media.browse.MediaBrowserService` for legacy clients) — `MediaLibraryService.SERVICE_INTERFACE` is a genuinely different string, not a supertype the old filter would still match. Service is `android:exported="true"` (Auto binds cross-process); `res/xml/automotive_app_desc.xml` + a `com.google.android.gms.car.application` `<meta-data>` makes the app eligible to show up in Auto.
- `onBind()`: `MediaLibraryService.onBind()` returns the real session binder for session-interface intents (Auto, Assistant, legacy browsers) and `null` for our own Activities' plain explicit-component bind. Must be `return super.onBind(intent) ?: binder` — unconditionally returning our own `LocalBinder` breaks Auto/Assistant's connection.
- A `MediaLibrarySession` must exist immediately in `onCreate()` (`buildMediaSession(streamUrl = null)`) — `onGetSession()` must return non-null for Auto to browse even before anything has played. `buildMediaSession()` still releases/rebuilds on every real `startPlayback()`; the `null` case skips station extras on the session's `sessionActivity` intent, relying on `PlaybackActivity` reading the live station once bound.
- Browse tree is flat (root → all stations, `sortOrder ASC, id ASC`) via `onGetLibraryRoot`/`onGetChildren`/`onGetItem`. Station media items use `mediaId = streamUrl`.
- Tapping a station reaches `onAddMediaItems` with a bare `MediaItem`. This is **not** routed through `startPlayback()`/`buildMediaSession()` — rebuilding the session whose callback is currently executing isn't supported. Instead `startPlayback()` is split into `buildMediaSession(streamUrl)` (top-level entry points only: `onCreate`, `onStartCommand`) + `applyPlayback(streamUrl, isRetry)` (player/notification/timeshift/retry pipeline, safe to call reentrantly). `onAddMediaItems` resolves the tapped `mediaId` against `cachedStations`, calls `applyPlayback()` directly, and returns an empty item list.
- `loadBrowsableStations()`/`playFromBrowseTree()` are `internal` (not `private`) so `RadioPlaybackServiceAutoTest` can exercise the DB → media item → playback pipeline directly — media3's own `MediaBrowser` Binder round-trip tests need instrumentation (`androidTest`), which this project doesn't have.

## Home screen widget

- `widget/RadioWidget.kt`: Jetpack Glance `GlanceAppWidget` (`widget/RadioWidgetReceiver.kt` + `res/xml/radio_widget_info.xml`; `android:initialLayout` is a required-but-unused placeholder, Glance replaces it at render time). Shows last-played/current station + play-pause + skip, dark palette matching `ui/theme/Color.kt`.
- `ui/playback/WidgetStateStore.kt` (separate from `PlaybackStateStore` on purpose): `PlaybackStateStore`'s contract is "last *started*, cleared on explicit stop" (for process-death resume); the widget wants to keep showing the last station with a play affordance even after an explicit stop. `RadioPlaybackService.updateWidget()` writes it and calls `RadioWidget().updateAll()` at the end of every `refreshSnapshot()`.
- Button taps are `ActionCallback`s in `widget/WidgetActions.kt`: `TogglePlaybackAction` (stops via `RadioPlaybackService.ACTION_STOP` — a widget `ActionCallback` isn't a bound instance, so it can't call `stopPlayback()` directly) or resumes; `NextStationAction`/`PreviousStationAction` use `util/StationNavigator.kt` (pure, JUnit-testable next/prev index calc), wrapping at either end. `ActionCallback` requires a no-arg constructor (same as `Service`/`BroadcastReceiver`), so each resolves `RadioStationRepository.create(context)` itself.
- Testing: `RadioWidgetTest` uses `runGlanceAppWidgetUnitTest` against `RadioWidgetContent` (`internal`, node-tree assertions, no rendering). `WidgetActionsTest` calls `ActionCallback.onAction()` directly, asserting via `shadowOf(application).nextStartedService`. Both this and `RadioPlaybackServiceAutoTest`'s next/prev test hit the real `AppDatabase.getDatabase()` singleton (no injection seam) — each sticks to a single `@Test` method and defensively clears rows before seeding.
