# Testing: CI & screenshot tests

Roborazzi/CI-pipeline specifics — only relevant when touching `.github/workflows/ci.yml` or a Composable covered by a screenshot test. See `AGENTS.md`'s Testing section for the general Kotlin/Robolectric gotchas that apply to any new test.

- Screenshot tests (`StationItemScreenshotTest`) use Roborazzi over Robolectric Native Graphics (`@GraphicsMode(GraphicsMode.Mode.NATIVE)`). Capture with the plain `captureRoboImage { content }` lambda from `roborazzi-compose`, not `createComposeRule()`/`createAndroidComposeRule<ComponentActivity>()` — this manifest has no `ComponentActivity` launcher entry, and the lambda form self-registers `RoborazziActivity` at runtime instead. Reference images live in `app/src/test/screenshots/` (`build/` is gitignored, so the Roborazzi default output dir wouldn't be). `./gradlew recordRoborazziDebug` re-records after an intentional visual change (review the diff); `./gradlew verifyRoborazziDebug` (in CI's `test` job) fails on any pixel diff — plain `./gradlew test` doesn't. **Baselines are recorded on Ubuntu** — font-rendering differs enough by platform that running `verifyRoborazziDebug` locally on macOS fails with a full-image diff even with zero relevant changes; don't re-record from a local non-Ubuntu run.
- **CI's `test` job runs `test` and `verifyRoborazziDebug` as one `./gradlew` invocation, not two separate ones.** Both ultimately depend on `:app:testDebugUnitTest`, and Gradle only executes a given task once per build graph — but two *separate* `./gradlew` invocations configure that task's inputs differently (Roborazzi's verify-mode system properties), so Gradle treats it as dirty and reruns the entire ~40-class Robolectric suite on each invocation (confirmed in practice: the Roborazzi-verify-mode rerun was itself ~5x slower than a plain run, 3m26s vs 38s for the same suite — screenshot capture itself is trivial, the cost was rerunning everything else under it). Don't re-split this into separate steps for readability; do it via `run: |` with distinct commands if per-step failure attribution is ever needed, not separate `./gradlew` calls.
- **`koverXmlReportDebug` is deliberately its own CI step, not merged into the one above** (`timeout-minutes: 8` + `continue-on-error: true`). Kover's coverage javaagent stacked on top of Robolectric's own bytecode-instrumenting classloader has been observed to hang `:app:testDebugUnitTest` indefinitely — confirmed via full job logs: the task started and then produced zero completed test classes for 27+ minutes before manual cancellation, not merely slow. Coverage is informational only (no `koverVerify` gate, see AGENTS.md's Testing section), so this step must never be allowed to block the actual test signal or eat unbounded CI minutes. Root cause (Kover/Robolectric classloading interaction) is unconfirmed/unfixed — if it starts hanging again even with the timeout, the next step is probably trying a different Kover coverage engine or excluding the Robolectric-native-graphics test classes (`IconStorageTest`, `StationItemScreenshotTest`) from instrumentation.
- **Before pushing any change that touches a Composable covered by a screenshot test** (currently `StationItem`, via `StationItemScreenshotTest`): `./gradlew test` alone is not sufficient sign-off — it runs Roborazzi's capture step but not `verifyRoborazziDebug`, so a changed icon/border/color silently passes locally and only fails in CI. Since baselines can't be correctly re-recorded on macOS (see above), the fix-forward loop is: push, let CI's `verifyRoborazziDebug` fail and name the affected tests, then re-add the temporary `record-screenshots.yml` workflow (`workflow_dispatch` running `./gradlew recordRoborazziDebug` on `ubuntu-latest`, see git history: `27d145f`, `03cd491`), trigger it, download the `roborazzi-screenshots` artifact, replace the PNGs in `app/src/test/screenshots/`, commit, and delete the temporary workflow again.
